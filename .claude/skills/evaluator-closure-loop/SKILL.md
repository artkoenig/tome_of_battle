# Evaluator Closure Loop

## 1. What this skill does

This skill is the driver of the unattended evaluator coverage-closure campaign. It alternates two phases:

- **Phase A — search.** The `evaluator-constraint-explorer` skill pins one uncovered cell per invocation with a black-box E2E scenario.
- **Phase B — implement.** The `uroboros:agile-loop` workflow closes the pinned gaps by changing `src/evaluator/` production code, driven by a campaign issue built from the open gaps.

The driver keeps every fact of the campaign on disk and re-arms itself for the next run until the campaign is closed. It never authors a scenario and never edits evaluator production code itself: phase A delegates the first, phase B the second.

## 2. Fixed constants

These are values, not knobs. State them, do not negotiate them.

- `CELL_CAP = 6` — cells per run, the fixed per-run cap.
- `CELLS_PER_PASS = 3` — cells per phase-A pass; a run therefore has two phase-A passes with one phase-B round between them.
- `MAX_GAP_ROUNDS = 2` — implementation rounds per pinned gap before it is parked.
- `RE_ARM_DELAY = 60 minutes`.
- `CAMPAIGN_BRANCH = claude/evaluator-coverage-campaign` — the one branch the campaign runs on.

## 3. State on disk

Four files hold the campaign. A fresh session resumes from these alone: never keep a campaign fact only in the conversation.

- `docs/testing/worklist.json` — generated by the inventory; the uncovered cells, sorted heaviest first. `totals.cells`, `totals.covered` and `totals.uncovered` are the numbers the run report quotes.
- `docs/testing/covered-cells.json` — the manual covered/waived record. The explorer writes it; the driver only reads it.
- `docs/testing/campaign-state.json` — `pinnedGaps` and `parkedQuestions` belong to the explorer; the driver reads them and never writes them. Everything the driver records lives under the single top-level key `driver`.
- the campaign issue directory under `docs/issues/` — `issue.md`, rewritten per phase-B round, plus the `backlog.json` that `uroboros:agile-loop` keeps beside it.

### The `driver` key of `campaign-state.json`

```json
"driver": {
  "schemaVersion": 1,
  "branch": "claude/evaluator-coverage-campaign",
  "campaignIssue": "docs/issues/0147-evaluator-coverage-gaps",
  "runs": 0,
  "lastRunAt": "YYYY-MM-DDTHH:MM:SSZ",
  "lastRunOutcome": "rearmed | terminated | stopped-operational-failure",
  "reArmedFor": "YYYY-MM-DDTHH:MM:SSZ | null",
  "gaps": {
    "docs/testing/<slug>": {
      "cellKey": "<pipe-delimited cell key>",
      "attempts": 0,
      "status": "open | closed | parked",
      "lastRoundAt": "YYYY-MM-DD",
      "question": null,
      "questionStatus": "open | answered",
      "answer": null
    }
  }
}
```

`gaps` is keyed by the pinned gap's `scenario` path, because that path is unique per gap while a cell key need not be. An entry appears the first time phase B works that gap. Create the `driver` key with these fields and `runs: 0` when `campaign-state.json` does not carry it yet, and never touch the two explorer arrays while doing it.

## 4. Step 0 — prepare the run

- Refuse to start on a dirty checkout. Run `git status --porcelain`; if it prints anything, stop and report, because the campaign commits per cell and per round and would otherwise sweep up someone else's work.
- Read `driver.branch`. If `campaign-state.json` carries no `driver` key, this is the first run: create `claude/evaluator-coverage-campaign` off the current branch, record it, and commit the seeded `driver` key. Otherwise check out the recorded branch with `git checkout <branch>`, fetching it from the remote when the checkout does not have it.
- Never create a git worktree. The driver owns the branch, and the campaign has exactly one.
- Read `docs/battlescribe-data-format.md` once per session before the first cell, whenever this run will invoke the explorer — the explorer's own precondition asks for it and the driver's session is the same session.
- Increment `driver.runs`, set `driver.lastRunAt`, and commit.

## 5. Step 1 — fold in answered questions

Do this before any cell is taken.

- Scan `parkedQuestions` for entries with `status: "answered"`. An entry whose `answer` is null or empty is not answered: report it in the run report as still open and skip it. Hand a genuinely answered entry's cell to the explorer first in step 3, and pass the recorded answer into the invocation so the explorer can quote it into its delegation prompt. Do not rewrite the entry — the explorer owns that array and its own skill already picks up an answered cell like any other worklist entry.
- Scan `driver.gaps` for entries with `status: "parked"` and `questionStatus: "answered"` and a non-empty `answer`. Reset such an entry to `attempts: 0` and `status: "open"`, so the gap re-enters the phase-B task list, and quote the answer into that gap's task text in the campaign issue.
- Commit the state change before going on.

## 6. Step 2 — the termination check

Run these three, in this order.

1. `node scripts/evaluator-coverage-inventory.js` from the repository root. Read its exit code as the script's header defines it: `0` every occurring cell covered or waived; `1` the worklist is not empty — the loop's normal state, not a failure; `2` an operational failure (missing corpus directory, `parsererror`, unreadable JSON record). A tool wrapper that flags exit 1 as an error must not be read as a failure.
2. `npx vitest run src/evaluator` — the evaluator suite including the manifest-driven E2E runner.
3. Read `parkedQuestions` and `driver.gaps`.

**Exit 2 is a stop, never a termination.** End the run immediately without running any phase, set `lastRunOutcome: "stopped-operational-failure"`, report the `FAILURE` lines verbatim to the human, and re-arm as any unfinished run does — the campaign is not closed, and a human may have repaired the corpus by the next run.

**Terminated** when all three hold at once: the inventory exited 0, the evaluator suite passed with no failing case, and nothing is open — no `parkedQuestions` entry with `status: "open"` and no `driver.gaps` entry with `status: "parked"`. Then set `lastRunOutcome: "terminated"` and `reArmedFor: null`, commit and push, report the closure, and **do not call `send_later`**. That is the only condition that stops the re-arming.

Otherwise continue to phase A. The suite being red here is expected mid-campaign: every pinned gap is a committed red scenario, and `CLAUDE.md`'s "all unit tests must pass" is suspended for exactly those, as the explorer skill already records.

## 7. Step 3 — phase A pass

Take up to `CELLS_PER_PASS` cells, and never past the run's remaining `CELL_CAP` budget.

- Invoke the `evaluator-constraint-explorer` skill once per cell. It completes exactly one cell per invocation and commits that cell's work itself — the scenario directory, `covered-cells.json`, the regenerated `worklist.json`, the Testkatalog entry, and for a red scenario its `pinnedGaps` entry. Add nothing to those commits.
- Prefer the cell of an answered parked question from step 1; otherwise let the explorer take the next worklist cell by its own rule.
- Stop the pass early when the explorer reports that the worklist holds no takeable cell, or when the inventory exits 0.
- Count every invocation against the run budget, whether the cell came out green, red or parked.
- Never write a scenario, a manifest or a coverage record in the driver's own turn: authorship belongs to the `e2e-testcase-author` subagent, which only the explorer delegates to (ADR 0033).

## 8. Step 4 — phase B round

**The open task list** = every `pinnedGaps` entry with `status: "open"` whose `scenario` is not recorded in `driver.gaps` as `closed` or `parked`. That definition is what lets the driver close and park gaps without ever writing the explorer's array.

Skip the round when the open task list is empty, and say so in the report.

### The campaign issue

One issue directory for the whole campaign, recorded in `driver.campaignIssue`. Create it on the first phase-B round as `docs/issues/<NNNN>-evaluator-coverage-gaps/issue.md`, where `NNNN` is the next free four-digit number above the highest numbered entry in `docs/issues/`. Use the directory form, not the single-file form the repository's `CLAUDE.md` describes, because `uroboros:agile-loop` is handed an issue *directory* and keeps its `backlog.json` beside `issue.md`.

Rewrite `issue.md` before every round from the current open task list, to this shape:

```markdown
---
status: active
branch: claude/evaluator-coverage-campaign
pr:
---

# Evaluator gaps pinned by the coverage campaign

## Goal

Make every scenario listed below green by changing `src/evaluator/` production code. Each entry is a committed black-box E2E scenario whose expectations were derived from the catalog data alone; the scenario is the specification and the engine is what is wrong.

## Context

- The scenarios were authored by the `e2e-testcase-author` subagent under ADR 0033 and are pinned in `docs/testing/campaign-state.json` under `pinnedGaps`.
- `npx vitest run src/evaluator` runs the manifest-driven runner `src/evaluator/e2e.testcatalog.test.js` over them.

## Acceptance criteria

- <one bullet per open gap: the scenario path, the failing case labels, and the gap's `note` — what the catalog data demands — plus, where the gap was parked and answered, the recorded answer quoted.>

## Out of scope

- Changing, weakening or deleting any scenario under `docs/testing/` — its `.ros` files, its `scenario.json` and its `README.md` are the specification.
- Authoring new E2E scenarios; the coverage campaign's phase A does that.
- Any change outside `src/evaluator/` and its unit tests.

## Decisions

- The check command for this issue is `npx vitest run src/evaluator`.
- No version bump inside the campaign; the human decides that when the campaign branch merges.
```

### Running the round

With the checkout on the campaign branch, run the `uroboros:agile-loop` workflow and hand it the issue directory as `args.issueDir`. The workflow publishes whatever branch the checkout is on and merges each accepted increment back into it, so the fixes land on the campaign branch and phase A continues on top of them. It also opens the pull request itself, so never open one yourself.

### Resuming versus starting a round

If `<campaignIssue>/backlog.json` exists and its run is unfinished, start the same workflow on the same directory again — it resumes and skips every recorded step. Never start a fresh issue directory to retry. Only when the previous round finished and new gaps are open, rename `backlog.json` to `backlog.round-<n>.json` before rewriting `issue.md`, so the new round starts from a clean run state while the record of the old one survives. Track `n` as `driver.runs` at the time of the round.

### Judging the round

After the workflow returns, run `npx vitest run src/evaluator` and decide per gap on that run's output.

- Every case of the gap's scenario green → set `driver.gaps[<scenario>].status = "closed"`.
- Still red → `attempts += 1` and `lastRoundAt` today. When `attempts` reaches `MAX_GAP_ROUNDS`, set `status: "parked"` and `questionStatus: "open"`, and write a `question` a human can answer without opening a file: what the scenario demands, what two implementation rounds failed at, and what decision would unblock it. A parked gap leaves the task list and is never handed to another round until its question is answered.
- Commit the `driver` state and push the campaign branch.

## 9. Step 5 — phase A again

Run step 3 once more with the run's remaining budget, because a landed fix can make new cells reachable and because the worklist is regenerated by every inventory run. Run it even when phase B was skipped — then it is simply the search continuing.

## 10. Step 6 — close the run

### Report to the human

The last message of the run, in this shape:

```
## Evaluator closure loop — run <driver.runs>

Coverage: <totals.covered>/<totals.cells> cells covered, <totals.uncovered> uncovered (docs/testing/worklist.json)
Phase A: <cells this run, each with its key and green/red/parked outcome>
Phase B: <campaign issue path> — closed <n>, still red <n>, parked <n>
Evaluator suite: `npx vitest run src/evaluator` — <passed>/<failed>

Parked questions waiting on you (<n>):
1. <cellKey or scenario> — <question>
   Answer it in <docs/testing/campaign-state.json>: write the answer into that entry's `answer` and set `status: "answered"` (a parked gap: `questionStatus: "answered"`).

Next run: re-armed for <local time> | none — the campaign is closed
```

List both sources of parked questions: the explorer's `parkedQuestions` entries with `status: "open"`, and `driver.gaps` entries with `status: "parked"`. Say "none" explicitly when there are none — the human must not have to guess whether the section was omitted or empty.

### Re-arm

At the end of every unfinished run — including a run stopped by inventory exit 2 — call the `send_later` tool with a delay of about one hour and a message that re-invokes this skill, for example: `Continue the evaluator coverage-closure campaign: run the evaluator-closure-loop skill.` Record the scheduled time in `driver.reArmedFor` and set `lastRunOutcome: "rearmed"`. Re-arm exactly once per run. If the tool is unavailable in the session, say so in the report and ask the human to re-invoke the skill in an hour — never substitute a sleep, a background process or a cron entry. Do not re-arm when the run terminated (step 2).

### Commit and push

The driver's own commits carry only `docs/testing/campaign-state.json` and the campaign issue files, with messages in the form `chore(campaign): <what changed>`. Push the campaign branch at the end of every run, so a session that dies loses nothing.

## 11. Never

- Never write `pinnedGaps` or `parkedQuestions` — they belong to the explorer.
- Never author, edit, weaken or delete a scenario under `docs/testing/`, and never change a scenario's expectations to make the engine pass.
- Never change production code under `src/evaluator/` in the driver's own turn; phase B does that through `uroboros:agile-loop`.
- Never exceed `CELL_CAP` cells in one run or `MAX_GAP_ROUNDS` rounds on one gap.
- Never create a git worktree, never run the campaign on the repository's default branch, and never open a pull request yourself.
- Never keep a campaign fact only in the conversation: if a fresh session could not read it from the four state files, it does not exist.
- Never re-arm after termination.
